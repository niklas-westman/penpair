# Comparative evidence checkpoint

For a new screen family or a substantial variant of an approved design, copy the
[checkpoint template](../assets/visual-checkpoint.md) into the project's review
folder before building. Use the project's existing report format if it retains
the same evidence. The copy is project-owned; never keep completed records inside
an installed skill folder, where `skills install --force` may refresh templates.

Record one representative case first. Link the actual approved image and complete
inspection with file/page/frame identity, revision, approval/case identity and
relevant component/token evidence. State which regions keep their layout,
hierarchy, density, type scale and native instances, and which intentionally
change. A sentence naming a reference does not establish that its image was seen.
If the task has no approved reference, record that limitation and the chosen
design direction; do not manufacture provenance or turn a draft into a baseline.

Before expanding devices/themes/states, export the candidate until stable, look
at source and candidate and record the consequential findings. Use a side-by-side
view at comparable scale; compare preserved regions separately from intentionally
changed content. Whole-page pixel equality is inappropriate for different data
states. A clean token/overflow audit and a generated screenshot do not establish
visual critique. Recomposition is allowed within the task's scope when its reason
and deviations are explicit; owner acceptance stays separate.

Expansion is ready only when the representative candidate has real source and
candidate evidence, a recorded critique and resolved blocking findings. Missing
images, unobserved instance behavior or failed readback remain pending. If
repeated failures or substantial tooling work prevent this result, report the
current evidence, effort and revised approach before adding a renderer or a larger
case matrix. Preserve source/library objects and stop ambiguous write retries.

For frontend work, carry the case record through handoff and browser comparison:
retain the route, viewport, theme, state, fixture, fonts, setup/provider identity,
baseline hash, observed screenshot and rerun result. Use `penpair-verify` when
installed. Design-to-design critique does not satisfy frontend verification, and
browser comparison does not approve a new design. Another agent should be able to
continue from the record's next action without guessing which artifact was judged.
