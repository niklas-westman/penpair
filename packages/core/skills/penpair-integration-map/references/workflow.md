# Integration reconciliation workflow

## Connect intent to responsibilities

Read the exact linked journey and inspect existing code before proposing routes,
components or data flow. Retain every linked journey requirement ID and connect
each local requirement through node/edge `requirementIds`. Missing coverage blocks
readiness; a graph may still be rendered as a visibly incomplete draft.

For each discrepancy record requirement, observation, evidence, user impact and
next action. For example: proposed retry preserves the address, while a real
failed-request observation clears it. Do not claim this mismatch without actual
browser/code evidence; a hypothetical example remains labeled hypothetical.

## Accept changes without inventing approval

Managed native semantic changes produce a canonical proposal plus an adjacent
`.native.json` observation. Preserve both. Acceptance checks the exact base and
fresh native observation, then reconciles the canonical contract and projection;
it cannot approve the resulting revision. A layout-only presentation proposal
keeps the canonical hash unchanged but replaces native presentation evidence and
requires renewed visual review. Never promote it to semantic or image approval.

Implementation agents read context, follow reviewed scope, observe actual state,
attach browser/behavior evidence and reconcile requirements afterward. Functional
checks, accessibility assessment, visual critique and owner acceptance remain
independent. Finalized design context is not implementation acceptance.

Native proposal acceptance uses a live read-only observation to reject edits made
after import. After semantic acceptance, republish explicitly to update native
contract metadata, then review the new artifact. A purely local semantic proposal
without a native observation can be accepted offline. Preserve accepted node
positions/sizes when republishing.
