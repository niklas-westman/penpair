# Comparison and implementation handoff

Carry the canonical release identity and complete resolved case inventory into
`penpair-handoff`, then `penpair-verify` when those skills are installed. Obtain
approved context and disclose its offline/live scope and any truncation. Never
implement from incomplete context while claiming the whole release was covered.

A finalized design is a reviewed design target, not implementation acceptance.
An unchanged historical design approval can remain valid while its application
comparison must run again against the current implementation.

For native mode, inspect installed `reflection check` help. It uses a trusted
`createReflectionConfig(request)` builder, exact engine version and public raw
report bridge. Published Reflection 0.7.0 alone lacks the required measured-capture
and managed-baseline capability extension. If those capabilities are unavailable,
keep native readiness pending; the reviewed custom provider remains supported.
Do not imply that installing the adapter or engine completed this integration.

For any release-bound comparison, generate the context with
`design-release context --from FINAL_RECORD --out CONTEXT_FILE`. It must contain
`releaseReference.record` and `.bundle`, each with exact project-relative path
and SHA-256, in addition to the full case inventory and policy. Regenerate older
contexts missing these references; never hand-add ready/finalized flags or hashes.
Native and custom-provider paths reload the actual finalized proof and require
matching approved image hash/scale, file/page/frame, route, case and threshold.
A context summary or Projection view alone cannot establish that binding.

## Run and inspect

Use installed comparison help and the project-owned route/setup mappings. Keep
viewport, scale, locale/timezone, theme, state, fixture, fonts and capture policy
explicit. Independently measured observations must come from the actual browser,
not copied requested config or metadata. Preserve the approved comparator policy
and per-case thresholds; do not raise thresholds to make a migration pass.

Capture all expected release cases, including retained ones. Partial selections
are useful diagnostics but cannot satisfy full-release implementation acceptance.
Validate the command envelope and case inventory, not just passing returned rows.
Missing mappings, pending cases, capture failures or cancellation remain incomplete.
Exceptions may cover reviewed bounded visual deviation, never missing proof.

Preserve the selected reference and original hashes in each run's immutable
evidence. Review sheets must show that run's verified artifacts, not newer images
at reused paths. An engine-produced decoded image is not proof of the original
approved WebP bytes. Do not invoke a baseline-update command on Penpot-owned
approved references.

After comparison, attach its release-bound report for assessment without editing
the finalized design:

```sh
penpair design-release status --from RELEASE_FILE --comparison REPORT_FILE
```

The same `--comparison` option is available to `check` and `context`. The report
must bind the exact design hash and full expected case inventory and `caseThresholds` policy. Context `implementation` is historical;
read `implementationAssessment` and `workflow.implementation` for the current
comparison. A passing report
can establish measured comparison, but owner acceptance remains `not-recorded`
until actual owner review; do not mark it accepted in chat or mutate frozen
implementation fields.

## Accept separately

Inspect screenshots and diffs, correct scoped implementation problems and rerun.
Report measured comparison, owner visual acceptance, accessibility and real-auth/
end-to-end checks separately. A fixture pixel check establishes none of the other
gates by itself. Keep implementation results separate from the frozen design
record; do not rewrite design evidence to fit a failed implementation.
