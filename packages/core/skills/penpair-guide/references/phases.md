# What to ask and explain in each phase

Use this when a phase starts. Keep every explanation to a few sentences, and ask for one thing at a time. The person decides; you read the state and say what it shows.

## Say it like this

| Term | Say |
| --- | --- |
| Pinned file | The design file Penpair is tied to |
| Frame | One design of a page at one size |
| Mood page | A page that holds your references and the feel you want |
| Approve | You tell me in your own words that this exact image is good |
| Journey map | A drawing of how a visitor moves through the pages |
| Integration map | A list of what each page needs from the app: routes, parts and data |
| Release | A numbered snapshot of the approved design (1.0.0 for the first) that the app is built from |

Never show the person phase numbers, skill names or record IDs unless they ask.

## 0. Connected

Explain: Penpair works through a Penpot design file that is open in a browser tab and visible. Ask: whether the tab is open on the right file. Evidence: `doctor` is healthy and the file is pinned.

## 1. Direction

Skip this when they already have a direction: write it in the project facts and move on. Explain: before drawing anything, collect a few references and agree how the product should feel, so every later page agrees. Ask: for three to five references (sites, screenshots, colours, type) and for the feeling in a few words. Evidence: a page named `Mood` with the references and a short note, and the same direction written in the project facts. Creating the page is a write, so preview it and ask first.

## 2. Structure

Explain: a website is a set of pages; each gets its own page in the design file so nothing is mixed. Ask: for the list of pages in plain words (home, pricing, contact) and which one most visitors see first. Evidence: one Penpot page per site page, named as the person calls them, plus a reviewed journey for the main flows. Never create the pages without a yes.

## 3. First frame

Explain: design one page fully before the others; what is learned there carries to the rest. Pick the most typical page, not the simplest. Ask: which page, and what it must let a visitor do. Evidence: a frame named `Desktop` at 1440 wide that has been exported and looked at twice (the skill that builds frames does this), and the owner's actual words approving that exact image. If frames already exist without an approval, show the person the image and ask; do not treat the frame as approved.

## 4. Other sizes

Explain: the same page needs to work on a tablet and a phone. Tablet and Mobile are derived from the approved Desktop frame so the three agree. Ask: whether the default widths (768 and 390) fit, or which devices matter. Evidence: `Tablet` and `Mobile` frames beside `Desktop`, each looked at and approved separately.

## 5. Every page

Explain: the remaining pages follow the same loop, one at a time, reusing what the first page settled. Ask: which page next. Evidence: for each site page, an approval record whose page and frame IDs match its three frames.

## 6. Connect to the app

Explain: this says which route, component and data each page uses, so the people building the app do not guess. Ask: whether the app already exists. Evidence: a reviewed integration map.

## 7. Release

Explain: a release freezes the reviewed design under a version number so the build can point at exactly what was approved. Propose it only when the release rule in the main guide is met. Ask: the owner for the version and for their words approving the release. Evidence: the release status reports the design as ready and finalized.

## 8. Build and check

Explain: the app is built from the released design, then compared with it in a real browser. Ask: where the app lives and how to run it. Evidence: comparison evidence exists, with differences resolved or reported.
