# Design release evidence and recovery

## Readiness

Start and continue from the installed CLI's authoritative release status. The
checkpoint identifies the current step and next valid action. Do not substitute
this workflow's ordered headings for the actual evidence assessment.

The resolved inventory includes changed frames and retained frames from the
exact finalized base. The new Penpot page contains changed frames, required
native maps and an overview linking to all active members. Check actual links to
the effective page/frame, not same-name matches. Each retained frame keeps its
original source identity and approval; each changed target needs its own review.

A release plan uses actual complete source inspections and reviewed journey and
integration contracts. Each local map requirement needs graph coverage, and an
integration contract retains all linked journey requirement IDs. Unknown required
native fields, unresolved blockers or stale hashes cannot become a verified
release merely because its overview renders.

Assembly prepares owned overview/map sections. Copy changed source frames only;
retained frames remain on earlier pages. Guided native copy/paste stays inside
the same pinned file. Retain explicit source-to-target root receipts for copied
frames; retained frames need independently verified continuity, not invented copy
receipts. Verify ordered child topology, references,
component/override/token/asset identity, interactions and sizing behavior.
Do not detach native objects, rasterize a screen or change auto sizing to ease
comparison. Independent source/target inspections and stable exports supply
proof; an acknowledgment alone supplies none.

After changed-frame copy, preview `design-release assemble --from RELEASE_FILE
--receipts RECEIPTS_FILE`, then apply the reviewed overview refresh with `--apply`.
The first assembly cannot know newly pasted target IDs. Refreshing assembly from
explicit receipts binds overview links to the actual changed targets; retained
links already use their original identities. Only then run `verify --receipts`
with the same reviewed mapping. Verification is remote read-only and cannot repair
an outdated overview. For schema-2 copied targets, receipts also carry the exact
target image approval references (`record`, `recordId`, `image`); source approval
does not approve a newly copied identity.

## Retained-frame continuity

Verify every active frame live before finalization. An earlier approval remains
an immutable reference: original source identity, case intent, approved image
bytes and exact owner record. A new observation has its own revision/time.
Continuity must verify both without rewriting the old approval or claiming a new
one. An unrelated file revision alone need not invalidate an otherwise proven
unchanged reference; missing evidence must still block it.

Use the shared CLI eligibility decision for coverage, case approval and browser
planning. Changed source identity, native structure, dependencies, capture policy,
case intent or approved pixels breaks continuity. A missing old page/frame cannot
silently become a frozen-only reference. Report the affected cases and preserve
the previous complete baseline generation after failed capture.

## Finalization and later drift

Keep map review, target image approval and exact release-candidate owner words
separate. Save immutable local evidence before updating the remote release
marker, verify that marker independently and publish the local final pointer
last. On interruption, retain the journal and compare saved bundle/remote marker
before attempting recovery. Local and remote operations are not one transaction.

Native release objects can change through shared components/tokens. Later checks
must expose drift without replacing frozen evidence. A new lossless WebP baseline
has new bytes and requires matching review; existing approved PNG bytes are
preserved unless migration is explicit. Design finalization leaves implementation
`not-assessed`; actual browser/behavior evidence and implementation acceptance
come later.

## Current supported verification limits

Native copy/paste is not complete native fidelity support. Verification currently
blocks all component instances, copies, main instances and component roots
because complete override state is unobservable. It also blocks groups lacking
an explicit `maskedGroup` observation, unknown mixed-range text/style state and
any other unknown or missing required field. Paths/vector shapes also block when
their actual native path content was not observed. Equal images and retained links do
not waive those limits. Keep selected screens blocked with the actionable reason;
never detach, flatten, strip styles or rasterize to obtain a pass. Extend and
validate the missing inspection support or obtain complete evidence first.

Pin each source's complete `inspection` path/hash and stable PNG `render`
path/hash before fidelity verification. Token-bound sources additionally require
complete pinned token-inspection `dependencies`. Drafts missing render evidence
can be prepared but cannot verify or finalize.

Release context carries actual frozen `mapContexts` and a `proposedBaselines`
configuration fragment with stable case IDs, WebP format, baseline root and
effective per-frame page/target IDs for the full resolved inventory. Review and merge that fragment deliberately; it does not modify
config or confer target image approval. Frozen design context and implementation
acceptance remain separate.
